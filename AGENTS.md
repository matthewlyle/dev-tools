# Agent rules for dev-tools

Native SwiftUI app for macOS 26, iPadOS 26, and iOS 26: a Plex Media Server API playground. These are the rules that aren't obvious from the code.

## Comments: almost never

Default to none. Code says *what*; a comment is only for a *why* the code can't carry. The bar: would a competent reader, six months from now, otherwise change this and break something?

Keep only:
- An external constraint — a Plex quirk, a HIG rule, a SwiftUI/AppKit limitation, a performance cliff — and what it forces here.
- A deliberate policy that looks like an omission (`// Credentials are shown masked and can't be copied out, by design.`).
- A non-obvious invariant or ordering dependency.

Never:
- Restate the code, name the type, or narrate steps (`// Set the title`, `// { [`).
- `// MARK:` — the files are short; organise with types instead.
- Doc comments on things whose signature already says it all.
- TODOs. Do it or drop it.
- Anecdotes. State the constraint, never the encounter: no "this showed up as", "we would have missed", "the X case", counts, timings, or specific values met along the way. A rule must stand without its origin story; the story belongs in the commit message.

A `///` on a type or function is fine when it meets the bar above; most don't. When you touch a file, delete comments that fail the bar. Commit messages carry the narrative, not the source.

## Load-bearing decisions

- **Tokens are never shown and never in a URL.** `X-Plex-Token` travels only as a header — the notification WebSocket included; `PlexRequest.url(base:)` cannot emit it; cURL export uses `$PLEX_TOKEN`; masked values have no copy path. What a server sends back — response bodies and headers, notification frames — goes through `CredentialRedactor` before anything shows, copies, or parses it: values under a token name (JSON key, XML attribute, `X-Plex-Token` query item, the `PlexOnlineToken` setting) and every known token are masked, so a new view of a response inherits the masking instead of adding its own. Artwork goes through `ImageStore` for the same reason — server art through `PlexHTTP`, public art on its own ephemeral session with no URL cache, since the privacy policy promises artwork stays in memory. Never `AsyncImage`: it fetches through `URLSession.shared`, which caches to disk. Do not add a reveal, toggle, or query-string option.
- **Tokens are never written outside the Keychain, and only go where they're verified to belong.** The account token's item is `…AfterFirstUnlockThisDeviceOnly`, so a backup can't carry it to another device; that only binds on iOS, because the Mac build uses the file-based keychain: the data protection keychain needs an application-identifier entitlement, which the Developer ID build has no provisioning profile to grant. `PlexResource` doesn't encode `accessToken`, so `servers.json` never holds one; server tokens come back with each `/api/v2/resources` refresh. Connection probes hit `/identity` without the token — an advertised local address can be anyone's off the server's own network — and the token goes only to a connection that answered with the server's machine ID. Every HTTPS connection ranks above any plain-HTTP one (`Connection.rank`), and an `httpsRequired` server's HTTP connections aren't probed. URLSession forwards every header through a redirect, so every session that carries a token uses `SameOriginRedirects`: a redirect off the origin comes back as the 3xx response.
- **A token typed into a request is sent but never kept or handed out.** `PlexRequest.withoutCredentials` drops `X-Plex-Token` from the path, params, and headers; history and saved requests store that form (and scrub older files on load), Copy URL and cURL export use it, and the URL preview masks it. A replayed or reloaded request therefore goes out with the server's own token.
- **The server is the scope, chosen from the title.** The window title is the selected server and its title menu (`toolbarTitleMenu` → `ServerMenu`) switches it and holds Server Info… and Refresh Servers — the HIG's document menu beside the title — with the same list in the **Server** menu bar menu. On iPad and iPhone the title menu also ends with Settings… after a divider: it's iOS's one always-present in-window menu, so settings stay out of the toolbar without a trailing More button; the Mac's title pull-down doesn't get it (it has the Settings scene). Nothing else earns a header button. There is no servers sidebar: a sidebar is for navigating areas of an app, and a server isn't an area, it's what every area is a view of. Endpoints / History / Activity / Media are views onto the selected server, never peers of it. Saved requests are a pinned group *inside* the endpoint list, not a section or a scope. The account (avatar, Sign Out…) lives in Settings, plus the App menu.
- **Every toolbar item has a menu bar command** (`AppCommands.swift`), except the section switcher and the compact tab bar that stands in for it — that's view navigation and lives only in the toolbar. Un-undoable destructive actions confirm.
- **Code face is Commit Mono** through `Typeface` / `Font.code(_:)`. Never `.monospaced()` or `NSFont.monospacedSystemFont` directly.
- **Large bodies:** wrap is forced above 256 KB and JSON is pretty-printed above the highlight limit. Unwrapped text in `NSTextView` lays out the whole document on the main thread. Don't relax either. The body text view is always the scroller — never inside a page `ScrollView` (that forces full layout). The request/response block scrolls *with* it because `CodeTextView` hosts it inside the text view's own scroll (top content inset = header height; header hosted via `NSHostingController`/`UIHostingController`, environment handed over with `.environment(\.self, context.environment)`). It ignores the bottom safe area and insets its content by the live `safeAreaInsets.bottom` instead (`contentInsetAdjustmentBehavior` is `.never` for the header inset), so the body runs under the tab bar and fills the room the bar gives up when it minimizes.
- **WebSocket path is `/:/websockets/notifications` (plural).** Plex's own OpenAPI doc lists it singular, which the server 404s. There is no EventSource transport; don't add one.
- **`Resources/plex-openapi.json` is generated** by `Tools/extract-spec.sh`. Never hand-edit it; fix consumers instead.
- **Response format (`Accept`) is an app-wide setting**, not per request. History replays use the current setting.
- **One universal target: macOS, iPadOS, and iOS (iPhone and iPad).** Views are shared SwiftUI; every platform difference goes through `Core/Platform.swift`, never a raw `NS*`/`UI*` type in a feature file. Images/fonts/colours are `PlatformImage`/`PlatformFont`/`PlatformColor`; clipboard is `Clipboard.copy`, opening a URL is SwiftUI's `@Environment(\.openURL)`, and the macOS-only modifiers have `platform…` wrappers (`platformTextStyle`). `#if os(macOS)` in a feature view is for genuine layout differences, not API shims (`onDeleteCommand`, the section switcher); reach for a helper in `Platform.swift` first. macOS keeps the `Settings` scene; iPadOS presents `SettingsView` as a sheet from Settings… at the end of the title menu and in the iPadOS 26 menu bar's App menu (`CommandGroup(replacing: .appSettings)`) — the HIG keeps settings out of toolbars, and the title menu is iPad's one always-present in-window menu. Both open the window header's sheet: the menu bar through the `showSettings` focused value, and `⌘,` is registered only on that menu bar command. Sandbox/hardened-runtime/entitlements are scoped `[sdk=macosx*]`. `CodeTextView` is an `NSTextView` on macOS and a `UITextView` on iPadOS behind one type, sharing the attributed-string renderer.
- **One header over the whole window on both platforms**: title (server + menu) leading, the segmented section switcher centre via `.secondaryAction`, the section's sort/clear actions trailing. A list's filter is a field pinned atop the list (`listFilter`), not a toolbar item — on macOS a `.searchable` toolbar search reconfigures the toolbar and reflows the switcher on every section change. macOS gets this from a two-column `NavigationSplitView` (section list | detail). iPad has no toolbar spanning split columns, so `MainSplitView` lays the list and detail out as two panes under one `NavigationStack` bar with `.toolbarRole(.editor)` — the role that keeps the title leading while `.secondaryAction` fills the centre. Never `.principal` on iOS: it replaces the title. That one bar has no per-column region, so a list's sort/clear as `.primaryAction` would land at the far right, over the detail; on iPad they sit beside the list's filter field instead. A list hands them to `listFilter`'s `actions`, which places them per layout — `.primaryAction` items over the column on macOS, in the tab's own bar on a compact width (each tab has its own bar there), trailing the field on a regular-width iPad.
- **All four sections stay mounted; the switcher only changes which is visible** (`sectionResident(active:)` in `MainSplitView`). Switching a `switch` branch tears a section down and rebuilds it, and the rebuild of a heavy section landed inside the switcher's animation on macOS. Resident sections make every switch instant; anything a section needs loads in its own `.task` after it's already on screen. The cost: an inactive section is still in the hierarchy, so anything that publishes to the window — `.sectionListToolbar` items, `.focusedSceneValue` commands — must gate on `@Environment(\.sectionIsActive)`, or Send/Delete would act on a section that isn't showing. `SectionListToolbar` does this already; a new focused value must. A section never declares its own `.inspector`: sibling inspectors in one column compete for the same presentation, so the detail pane hosts one (`SectionInspector`) that shows what the visible section has open, from state in its store.
- **A compact width is tabs, not two panes.** An iPhone, or an iPad in Slide Over or a narrow split (`\.isCompactWidth` in `Platform.swift`), can't hold the list beside its detail or the switcher beside the title, so `MainSplitView` makes each section a `Tab` whose `NavigationStack` roots the section's list and pushes its detail. It's the one place the sections look like app areas; they're still views onto the server — every tab's title is the server with its title menu (Settings… included), and there is never a Servers tab. A list brings its detail on screen through `@Environment(\.showSectionDetail)`, which is nil wherever the detail is already beside it: Endpoints on open, History on selection (a re-tap replays), Media on Run. Activity pushes nothing: its list pane only filters, so on a compact width the events are the tab's root and the type filter is a toolbar menu (`ActivityTypeMenu`). Endpoints' root has Edit Request, the toolbar twin of Focus Path (⌘L), because a path can't be typed until the request bar is pushed; Focus Path therefore survives a push (`pathFocusPending`, consumed by the bar when it appears). A tab switch keeps every tab's stack: sections share one `RequestStore` workspace, so a switch parks the outgoing section's request, response, and back/forward and restores the incoming one's (`switchWorkspace`); a server switch discards them all (`resetAllWorkspaces`) and pops the stacks. `TabView` keeps visited tabs mounted, so each tab sets `sectionIsActive` and the per-tab `Header` and `SectionInspector` gate their commands and presentation on it. An Activity event opens in a real half-height `.sheet` there (an adapted inspector opens full height on an iPhone whatever its detents say), with the events still live behind it. On iOS a Media item opens in a real `.sheet` wherever the detail is compact or taller than wide (measured outside the inspector, so opening it can't flip the choice), and in the side inspector otherwise. The sheet zooms out of the tapped poster (`.navigationTransition(.zoom)` against `matchedTransitionSource` on the art, through the `posterZoom` namespace `SectionInspector` hands down) and rests at the medium detent; an inspector can't zoom, which is why the phone's Media info is a sheet and not the adapted inspector. The zoom's timing, drag-to-dismiss, and Reduce Motion fallback are the system's — don't restyle them. A full-width iPad sheet ignores detents, so it lands as a centred card. Any sheet showing Media info carries its own `LightboxOverlay`; the window's is drawn under sheets. Size-class branches beyond the shell: the response block's info row goes to two lines (`ResponseInfoRow`) and parameter rows put the value under the name; everything else already fits the iPad's 260 pt list pane.
- **A section's list pane only filters or chooses what the detail shows.** On a regular-width iPad, Activity's list pane stays hidden until it has something to list: the panes share one well, so a blank one would be unmarked space pushing the events' zero state off centre. Status and controls for the detail's content live with it: Activity's connection (status, received count, last error, Connect/Disconnect) is `ActivityConnectionControl`: on an upright phone the tab bar's accessory (`tabViewBottomAccessory(isEnabled:)`, Activity's tab only — the reason iOS targets 26.1), one line, inline beside the tab bar when it minimizes; elsewhere (iPad, the Mac, a phone in landscape, where the accessory would span the screen) a glass capsule floating over the bottom of the events (`.safeAreaInset(edge: .bottom)`). Its list pane is the event-type filter alone. Status reads `Connected`, never the server's name — the title already says it. Disconnect-on-server-switch lives in `MainSplitView`, since the list pane isn't mounted on every layout.

## Design: the HIG, as applied here

We follow Apple's Human Interface Guidelines for macOS. Below is how that resolved in this app; when in doubt, read the HIG page, not another app.

**Chrome must earn its place.** Every visible control or label in a header costs attention. Before adding one: is it already shown elsewhere in the window (the title bar names the server — don't repeat it)? Could it be a tooltip, a popover, a menu item, or a Settings default instead? The request bar is `GET [path] [Send]`; keep it that way.

**Layout**
- Two columns at a regular width (a compact one is tabs; see above): the selected section's list, then its detail. Toolbar shape is fixed: title (server, with its menu) leading, one segmented section switcher in the centre (`.secondaryAction`), each section's sort/clear actions in the trailing slot. A list's filter is a field pinned atop the list (`listFilter`), never a toolbar search item. Never two segmented controls in the toolbar; SwiftUI has no column-aligned toolbar sections on macOS, so don't try to put items "over" a column. The list is user-resizable on both: macOS through `NavigationSplitView`'s column (260–800, 340 by default), iPad by dragging the pane divider (`ListDetailPanes`; `@AppStorage`, double-tap resets, VoiceOver adjusts it) — the kept width re-clamps to the window on every layout so rotation and Split View leave the detail at least 360 wide. The drag writes the width outside any animation; the pane tracks the finger.
- Column layout is narrow: lists use two-line rows, not tables; response headers are a `Grid` inside the tab's scroll so the request block can scroll with them. Sorting in a narrow list goes in a toolbar menu. A long column (the endpoint catalog, history) is a `SectionColumnList` (`LazyVStack`), never a `List`: on macOS `List` hosts every row in its own `NSHostingView` and measures them all when it appears, so hundreds of rows stall each section switch. Short columns (Activity, Media) keep `List`. A compact width is always iOS, where `List` is lazy, so there `SectionColumnList` is a plain `List` and its rows swipe (History: Delete; Saved: Delete…, Rename…).
- Sheets for short targeted input (save, placeholders); popovers for reference (endpoint docs); never a popover for a warning. No auxiliary windows. A sheet is framed by `SheetScaffold`: a fixed-width panel with bottom-trailing buttons on the Mac, a navigation bar on iOS with `role: .close` (✕) leading and `role: .confirm` (prominent ✓, titled for VoiceOver) trailing, resting at the medium detent with a grabber. Never a fixed width on iOS — an iPhone sheet is the screen's width and clips it; a popover that can adapt to a sheet takes an ideal width, not a fixed one.

**Toolbar placement** — decide this when adding the control, not at review.
- The toolbar is for things that act on *what the column shows*: switching the view, sorting it, clearing it. A list's filter is a field pinned atop the list (the system search field on a compact width), not a toolbar item. If a control edits or sends the *object being edited* — the request's path, params, headers, send — it lives beside that object in the request bar. Actions on the request as a whole — documentation, copy (a Copy menu: body, URL, cURL), and save — are toolbar items over it (`requestScreenActions`): the pushed request screen's bar on a compact width, the trailing end of the bar over the detail elsewhere, where apps keep actions on the document shown. The developer docs link sits in the documentation popover. If a control acts on a sub-pane (the Response pane's wrap, fold, copy body), it lives in that pane's own header row.
- Values and preferences are never toolbar items: a pop-up in the body, or Settings if app-wide.
- Status and information never go in the toolbar. Title and `navigationSubtitle` are the only text there.
- Each section owns the trailing slot and declares its own items from its view; when the section changes, its items go with it. Aim for at most three trailing items. A list's own sort/clear go through `listFilter`'s `actions`, not `.sectionListToolbar` directly: toolbar items over the column on macOS and in the tab's bar on a compact width, beside the field on a regular-width iPad (no per-column toolbar there), from the same `Menu`/`Button` views. Activity has no filter field; its Clear Events (and on a compact width its type-filter menu) are the events view's own `.sectionListToolbar` items, never inside the connection control.
- Toolbar items are icon-only `Label`s, no bezels, standard SF Symbols. A toolbar *command* must also exist as a menu bar command — the toolbar is never a command's only home, because users can hide or customise it. The section switcher (and the compact tab bar) is exempt: it's view navigation, not a command, and stays toolbar-only.
- The Refresh Servers class of rare actions belongs in the menu bar only; the toolbar is for what you do repeatedly.

**Menu bar** — Apple's rules, as they land in `AppCommands.swift`.
- The menu bar lists *every* command the app has (the section switcher is view navigation, not a command, and stays out of it). Toolbar buttons, context-menu items, and keyboard shortcuts are conveniences on top of a menu item, never substitutes for one.
- Put a command in the menu people expect: **App** (About, Settings… ⌘,), **File** (documents: save/open/close), **Edit** (text and clipboard), **View** (what's shown and how — Wrap Lines), **Window**, **Help**. App-specific commands go in custom menus between View and Window: **Server** (act on the selected server: Refresh Servers, Clear History…, Clear Events) and **Request** (act on the request in the bar: Save, Copy URL, Copy as cURL, Copy Response Body, Show Documentation, Open in Developer Docs, Send, Cancel, Focus Path, Back, Forward). Don't invent a third menu when one of these fits.
- Order within a menu: most frequent first; group related items with separators; keep menus short; submenus sparingly and one level deep.
- Labels are verb phrases in Title Case with no articles. Trailing `…` when the command needs more input before acting. A command that toggles uses a checkmark (inline `Picker`/`Toggle`) or a changeable label (Show/Hide); never both.
- Unavailable commands are *dimmed*, never removed — the menu's shape stays stable. Gate on state (`activeServer == nil`, `!requests.isSending`); for commands that act on the visible section, publish a `FocusedValues` action from that view and disable when it's absent.
- Shortcuts: `⌘` primary; `⇧⌘` for the sibling of a `⌘` command; `⌥` rarely; `⌃` never. Only frequent commands get one. Never repurpose a standard shortcut (`⌘Z X C V A F S W N Q ,` and the system's `⌘Space`, `⌘Tab`, `⌘←→`). Taken here: `⌘R` Refresh Servers · `⌘S` Save Request… · `⇧⌘C` Copy as cURL · `⌘↩` Send (runs the built query in Media) · `⌘⌫` Delete History Item · `⌘I` Show/Hide Info (Media poster, Activity event) · `⌘.` Cancel · `⌘L` Focus Path · `⌘[` `⌘]` Back/Forward · `⌘,` Settings · `⌘F` find in body (system). Add new ones to this list.
- Menu item icons: none, unless a whole group gets them.

**Liquid Glass**
- Don't apply `glassEffect` yourself. Glass is the system's controls/navigation layer — toolbar, sidebar, tab bar accessory, `.glassProminent` on Send. The one exception is Activity's connection capsule on iPad and the Mac: a control floating over content, which the HIG allows on a custom control "sparingly". A second one needs the same case: a control, above content, with no system home. Everything in a content pane (status readouts, pagination, badges, cards) uses standard fills: `.fill.tertiary`, `.quaternary`, `.regularMaterial`.
- The detail well (`WellBackground`) is the one sanctioned content-pane translucency: an `NSVisualEffectView` (`.underWindowBackground`, `.behindWindow`) that blurs the desktop like Safari's start page, behind opaque cards and the code document so they stay legible. It's macOS-only and user-toggleable (`translucentBackground`, default on) in Settings ▸ Appearance. Don't extend behind-window vibrancy to other content surfaces. iOS has no desktop behind the window, so its well is the system background under a static accent wash from the top (faint, gone by mid-screen, dropped under Increase Contrast); it backs every iOS screen — lists, details, sign-in — and on iPad one well spans the list and detail panes, with no pane colour or divider between them. The code surface's background is clear on iOS so the response body draws over the well too; an opaque code surface there turns the pushed body screen into a black slab beside the washed lists. The wash is the only gradient: never animated, never a raw colour.

**Controls**
- Segmented control = switching views. A *value* is a pop-up (`Picker` `.menu`), or a Settings default if it's app-wide.
- One prominent button per view (Send). Destructive actions use `role: .destructive`; only un-undoable ones confirm (Clear History, Sign Out, Delete saved) — Disconnect and Clear Events don't.
- Checkbox for a single minor option in the body (Wrap); switch only for an emphasised or grouped setting. Toggles never in a toolbar.
- Icon-only buttons are `Label("Verb", systemImage:)` + `.labelStyle(.iconOnly)`, never a bare `Image`, so VoiceOver gets the verb. Decorative symbols get `.accessibilityHidden(true)`. Status colours are always paired with words; the dot is redundant.
- A row in a selectable `List` opens through `.contextMenu(forSelectionType:menu:primaryAction:)` — a tap on iPad, a double-click on the Mac, where a click already selects — never a tap gesture or a row `Button`, which on macOS swallow the table's own click and arrow-key selection. On a compact width a tap neither selects nor runs the primary action, so there the rows are `Button`s that set the selection (Activity's events).
- Spinners are unlabelled; the sentence above them says what's happening. Never "Loading…". Don't block the panel while sending — the spinner replaces Send's icon and the last response stays readable.
- A section's *resting* or *empty-result* state (nothing sent, nothing queried yet, not connected, no events yet, a query or filter that matched nothing) is `ZeroState`, never `ContentUnavailableView`: one muted `subheadline`/`tertiary` sentence, no icon or heading, because the switcher already says where you are. A zero state never carries a button: a section's controls are always on screen (Activity's Connect is in the events' footer). Failures and missing prerequisites stay `ContentUnavailableView` with what to do next (Request Failed, Couldn't Connect, No Libraries, No Servers, a server that isn't reachable).
- Numbers that change in place roll with `.contentTransition(.numericText(value:))`.
- A field that takes epoch seconds is never bare: it gets `EpochDateButton` (calendar and Now; the relative ago choices only where the media-query grammar applies — Media filters, operator keys) and an `EpochReadout` under it. Which names are dates is `EpochDate.isEpochName`, shared with the decoded Details, so a field and its read-out never disagree.

**Colour, type, icons**
- System semantic colours only. Anything hashed to a colour maps into the 12-colour system palette, never raw HSL.
- The code surface is coloured by `CodeColors.system`: system hues (`PlatformColor.codeTeal` …) resolved to their Increase Contrast variant in a light appearance and left standard in dark: the code surface is white, where the standard teal, green, and orange fall far under 4.5:1. Add a token colour the same way, never a raw system hue. There are no code themes; don't add a theme setting.
- Text styles for hierarchy; no Light/Thin weights; no hand-set `.tracking`. Monospace only via `Font.code(_:)`, with rows stepped down on iOS through `.codeListRow` (lists) and `.codeDetailRow` (name/value grids), since iOS's text sizes set Commit Mono far larger than the Mac's; and it's for what the machine says: paths, keys, values, types, counts and count badges, timings, status and error readouts (the Activity status line, a history row's detail). Prose — descriptions, zero states, headings, controls — stays in the system face.
- SF Symbols used for their meaning. There are no OS/brand logos in SF Symbols: host marks come from bundled Simple Icons (`Assets/Hosts`, template vectors) plus `apple.logo`; Windows is hand-drawn. App icon is Lucide `braces` on the 1024 grid.

**Copy**
- Title Case for controls, menu items, headers, empty-state titles; sentence case for descriptions and status lines. Verbs on buttons. Trailing `…` when a control needs more input first (`Save Request…`, `Clear History…`). Errors say what to do, next to the thing that failed.

**Spec**
- The OpenAPI spec is a guide, not truth. `required` is frequently absent, so a documented-but-unsent parameter shows as a hint on a 400, not a block on sending. Documented params feed autocomplete; users can still type anything.

**Animation** — motion is for continuity and feedback, never ambient decoration.
- Animate when something *changes in place* and the user tracks it (a number updating, a disclosure opening, a state flipping), when content *arrives* (a result set, a decoded image, a live event), or to give an action *felt feedback*. Entrances rise-and-fade from near their resting place — never from `scale(0)` or off-screen; stagger a group 30–80ms apart, capped so a long list doesn't cascade, and never let it block interaction. Still banned: anything ambient or looping (breathing controls, shimmer skeletons, animated gradients, parallax) and motion on the code/response body (layout cost). Two loops are allowed, each running only while its state is real and static under Reduce Motion: a loading placeholder's fill breathing in opacity while its content is actually on the way (`PosterSkeleton`, told by `RemoteImage` whether it's still loading; it stops once there's nothing to wait for and never sweeps a shimmer), and Activity's signal rings swelling slowly while the notification stream is connected, so the screen reads as listening (`ListeningPulse`). Static layouts stay static.
- SwiftUI idioms: scope every animation to the value that changed with `.animation(_, value:)`, never a bare `withAnimation` around unrelated state. Numbers roll with `.contentTransition(.numericText(value:))`; swapped text crossfades with `.interpolate`, except a status word the user watches change (Activity's Connected ⇄ Disconnected), which rolls letter by letter with `.contentTransition(.numericText())`. Use the system springs rather than hand-tuned curves: `.snappy` for anything that moves, `.smooth` for large layout, `.bouncy` for a landing the user caused (a poster selected, a response arriving) — never for chrome. Leave system components (lists, disclosures, sheets, menus) to their own motion.
- Swaps are asymmetric: what's leaving gets out of the way faster than what's arriving, never a symmetric crossfade. A resting, empty, or error state goes through `restingStateTransition()` (arrives over ~0.3s, leaves in 0.1s; `rising:` only where the state doesn't carry the request bar, which must not move). A section switch cuts the outgoing section and settles the incoming one up 6pt as it fades in — never sideways. A transition's attached animation runs even in an unanimated transaction, so never attach one to rows that a workspace swap (`switchWorkspace`, `reset`) replaces.
- Reduced motion is a first-class variant, not an afterthought: read `@Environment(\.accessibilityReduceMotion)` and collapse movement to a crossfade or an instant change. Colour and opacity may still transition.
- Skills — run the animations.dev skills by phase, not as a sweep:
  - Designing a feature that has any motion in it → `find-animation-opportunities` first (read-only; it also says what should stay still), then `motion-brief` if the motion is more than a value change.
  - Implementing → `animate` for easing, duration, and spring choices; `animation-accessibility` for the reduced-motion variant.
  - Before committing motion code → `review-animations`. If it's a value update behind a `numericText` or a system component's own transition, skip the review; the bar is met.
  - `improve-animations` (whole-codebase audit) only when the user asks for one — the point of this section is to not need it.
  - Naming a motion you can picture but not name → `animation-vocabulary`.

## Feature definition of done

A feature is complete when every line below is true, in the same commit. This is what makes app-wide reviews unnecessary.

1. **Placement decided** by the toolbar rule above: column → toolbar; object → request bar; sub-pane → its header. Nothing repeats what the title bar shows.
2. **Menu bar command** in the right menu, dimmed (not hidden) when unavailable, shortcut only if frequent and not taken.
3. **Controls chosen by kind**: segmented for views, pop-up for values, Settings for app-wide preferences, checkbox for a single body option, `role: .destructive` on destructive actions, confirmation only if un-undoable.
4. **Accessible**: icon-only controls are `Label` + `.iconOnly`; decorative symbols hidden; colour never the only signal; a `.help` tooltip on every icon-only control.
5. **States covered**: empty (`ContentUnavailableView` with a next step), loading (unlabelled spinner, nothing blocked), error (inline, says what to do), and disabled when there's no server.
6. **Copy**: Title Case controls, sentence-case descriptions, verbs on buttons, `…` on commands that ask first.
7. **Motion**: anything that changes in place animates per the Animation rule, scoped to its value, with a reduced-motion variant; anything else stays still. Non-trivial motion has been through `animate` and `review-animations`.
8. **Token policy** holds: nothing new shows, copies, or URL-encodes a credential.
9. **Persistence** through `AppSupportStore`, `Codable`, tolerant of old files (unknown keys ignored, new keys optional).
10. **Tests** for any new contract — parsing, URL/string building, matching, redaction — none for plumbing.

## Working here

- Xcode project uses synchronized groups: add or move files on disk and they're in the target. No `pbxproj` edits.
- Build: `xcodebuild -project DevTools.xcodeproj -scheme DevTools -destination 'platform=macOS' -derivedDataPath DerivedData/Build build`. Test: same with `test` (Swift Testing, `DevToolsTests/`). Build iOS too with `-destination 'generic/platform=iOS Simulator'`. Both platforms and the tests must be green before a commit.
- A `Local` connection on an iOS device triggers the local-network privacy prompt (`INFOPLIST_KEY_NSLocalNetworkUsageDescription`); the simulator never asks, so networking changes need a device check against a LAN server.
- The Mac app ships outside the App Store, not through TestFlight: `Tools/release.sh` builds, notarizes, and staples the app, packs it into a notarized DMG, copies it to `site/DevTools.dmg`, and stamps the version into `site/index.html`. `site/` is the static landing page and privacy policy, deployed to Vercel with the CLI (`vercel deploy --prod` from `site/`). The DMG is gitignored, so a Git-integration deploy would ship the page without it. The privacy policy states what the app sends and stores; a change to either (a new host, a new stored file, anything identifying) updates `site/privacy.html` in the same commit.
- iOS ships through TestFlight: `Tools/upload-ios.sh` archives and uploads with `Tools/ExportOptions-iOS.plist`, which lets Xcode raise the build number. App Store Connect rejects an iOS icon with an alpha channel, so iOS has its own flattened `icon_ios_1024.png` (`Icon/build-icon.sh` writes it). `PrivacyInfo.xcprivacy` declares the app's required-reason API use (UserDefaults, CA92.1) and no collected data; a new required-reason API (file timestamps, disk space, system uptime, …) needs an entry there or the upload is rejected.
- Tests are fixture-driven and target contracts (parsers, URL building, spec matching, redaction, cURL). Add one when you add a contract; don't test plumbing.
- NEVER take screenshots (`screencapture`) or script/drive the running app for verification — it grabs the user's whole screen and is disruptive, and multiple app instances clash with their Xcode session. `xcodebuild` (build + `test`) is the verifier; reason from the code, and leave visual confirmation to the user, telling them precisely what to check.
- One commit per coherent change; the message explains why and records the constraint behind any non-obvious choice.
- SourceKit diagnostics in this workspace report the whole module as unresolved ("Cannot find type … in scope"). They are noise; `xcodebuild` is the verifier.
