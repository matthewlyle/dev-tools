# Agent rules for dev-tools

Native SwiftUI app for macOS 26, iPadOS 26, and iOS 26: a Plex Media Server API playground. These are the rules that aren't obvious from the code.

## Comments: almost never

Default to none. Code says *what*; a comment is only for a *why* the code can't carry. The bar: would a competent reader, six months from now, otherwise change this and break something?

Keep only:
- An external constraint — a Plex quirk, a HIG rule, a SwiftUI/AppKit limitation, a performance cliff — and what it forces here.
- A deliberate policy that looks like an omission (`// Credentials are shown masked and can't be copied out, by design.`).
- A non-obvious invariant or ordering dependency.

Never:
- Restate the code, name the type, or narrate steps (`// Set the title`, `// { [`).
- `// MARK:` — the files are short; organise with types instead.
- Doc comments on things whose signature already says it all.
- Describe what a view shows or how a feature behaves for the user. That's what the code and the running app are for.
- Document wiring (`Published by…`, `Set by…`, `Called when…`).
- Repeat this file. A decision recorded here carries no comment in the code.
- TODOs. Do it or drop it.
- Anecdotes. State the constraint, never the encounter: no "this showed up as", "we would have missed", "the X case", counts, timings, or specific values met along the way. A rule must stand without its origin story; the story belongs in the commit message.

A comment is one or two sentences. A *why* that needs more is a design decision: it belongs in this file or the commit message. A `///` on a type or function is fine when it meets the bar above; most don't. When you touch a file, delete comments that fail the bar. Commit messages carry the narrative, not the source.

Expect about 20 comment lines per 1,000 lines of code. A file or change well above that means the bar slipped: cut until it doesn't.

## Load-bearing decisions

- **Tokens are never shown and never in a URL.** `X-Plex-Token` travels only as a header — the notification WebSocket included; `PlexRequest.url(base:)` cannot emit it; cURL export uses `$PLEX_TOKEN`; masked values have no copy path. What a server sends back — response bodies and headers, notification frames — goes through `CredentialRedactor` before anything shows, copies, or parses it: values under a token name (JSON key, XML attribute, `X-Plex-Token` query item, the `PlexOnlineToken` setting) and every known token are masked, so a new view of a response inherits the masking instead of adding its own. Artwork goes through `ImageStore` for the same reason — server art through `PlexHTTP`, public art on its own ephemeral session with no URL cache, since the privacy policy promises artwork stays in memory. Never `AsyncImage`: it fetches through `URLSession.shared`, which caches to disk. Do not add a reveal, toggle, or query-string option.
- **Tokens are never written outside the Keychain, and only go where they're verified to belong.** The account token lives in the data protection keychain on every platform (`kSecUseDataProtectionKeychain`; on the Mac the `keychain-access-groups` entitlement, granted by the provisioning profile automatic signing adds, Developer ID included), in an `…AfterFirstUnlockThisDeviceOnly` item, so a backup can't carry it to another device. The file-based keychain asks for the login password whenever a build other than the one that wrote an item reads it; a token left there moves over on first read, and sign-out deletes both. `PlexResource` doesn't encode `accessToken`, so `servers.json` never holds one; server tokens come back with each `/api/v2/resources` refresh. Connection probes hit `/identity` without the token — an advertised local address can be anyone's off the server's own network — and the token goes only to a connection that answered with the server's machine ID. URLSession forwards every header through a redirect, so every session that carries a token uses `SameOriginRedirects`: a redirect off the origin comes back as the 3xx response.
- **The token only travels over TLS; there is no plain-HTTP path.** The machine ID is public and an on-path relay can pass a probe to the real server, so an `/identity` answer over HTTP proves nothing, and the token would cross the network in the clear. `ConnectionProber` never probes an HTTP connection, whatever the server's `httpsRequired` says, and `isHTTPS` comes from the dialled URI's scheme, not the `protocol` field beside it. The notification socket is always `wss`, and refuses to open on anything else. Don't add an insecure-connections option: people locked out fix the server or router, and relay and remote HTTPS still work. With TLS proving the server on every connection, a network change carries no token risk and needs no re-check.
- **Answers that outlive their moment are dropped.** A refresh answer is kept only if no newer refresh or sign-out started since (`ServerStore.generation`); a probe answer only if it's the entry's latest probe and wasn't cancelled. Every store cache that sign-out resets takes the same guard, a generation its loads check after each await. A connection that never answers holds out until the timeout, so probe answers land one at a time: a server is usable once one connection has proved it, a better-ranked one that proves it later takes over, and `isRefreshing` covers only the server list. While Activity is listening, a new `ConnectedServer` for its server reconnects the stream there; losing the connection doesn't disconnect it, since the stream retries on its own. A resume after background starts over on the current connection, never the stored one.
- **Sign-out ends the whole session, in `SignOutConfirmation`.** It's the one path to sign-out. The views that would otherwise stop the stream or drop state are unmounted with `MainSplitView`, so their `onChange`s never run: it tears everything down itself, the lightbox included (drawn over the sign-in screen, holding a `ConnectedServer`). `AccountStore.session` makes a restore or approval still in flight drop its answer rather than sign the old account back in. History, saved requests, typed placeholder values, and preferences stay: they hold no credential. A new store holding account or server state joins this teardown.
- **A token typed into a request is sent but never kept or handed out.** `PlexRequest.withoutCredentials` drops `X-Plex-Token` from the path, params, and headers; history and saved requests store that form (and scrub older files on load), Copy URL and cURL export use it, and the URL preview masks it. A saved request's name defaults to its path, so names go through the same stripping. A replayed or reloaded request therefore goes out with the server's own token. `PlexRequest.splitPath` takes text that isn't validly encoded (typed paths, server-sent keys, names), so it never hands raw text to a percent-encoded `URLComponents` setter, which traps.
- **The server is the scope, chosen from the title.** Its title menu (`toolbarTitleMenu` → `ServerMenu`) is the HIG's document menu. On iPad and iPhone it also ends with Settings…: it's iOS's one always-present in-window menu, so settings stay out of the toolbar; the Mac has the Settings scene instead. Nothing else earns a header button. There is no servers sidebar: a sidebar navigates the areas of an app, and a server is what every area is a view of. Endpoints / History / Activity / Media are views onto the selected server, never peers of it. Saved requests are a pinned group *inside* the endpoint list, not a section or a scope. The account (avatar, Sign Out…) lives in Settings and the App menu.
- **Large bodies:** wrap is forced above 256 KB and JSON is pretty-printed above the highlight limit. Unwrapped text in `NSTextView` lays out the whole document on the main thread. Don't relax either. The body text view is always the scroller — never inside a page `ScrollView` (that forces full layout). The request/response block scrolls *with* it because `CodeTextView` hosts it inside the text view's own scroll, as a top content inset the header's height; the hosting controller doesn't inherit SwiftUI's environment, so it's handed over with `.environment(\.self, context.environment)`. On iOS `contentInsetAdjustmentBehavior` is `.never` (automatic adjustment would stack the safe area on the header inset), so the view ignores the bottom safe area and insets by the live `safeAreaInsets.bottom` itself to run under the tab bar.
- **WebSocket path is `/:/websockets/notifications` (plural).** Plex's own OpenAPI doc lists it singular, which the server 404s. There is no EventSource transport; don't add one.
- **`Resources/plex-openapi.json` is generated** by `Tools/extract-spec.sh`. Never hand-edit it; fix consumers instead.
- **Response format (`Accept`) is an app-wide setting**, not per request. History replays use the current setting.
- **One universal target: macOS, iPadOS, and iOS (iPhone and iPad).** Views are shared SwiftUI; every platform difference goes through `Core/Platform.swift`, never a raw `NS*`/`UI*` type in a feature file. Images/fonts/colours are `PlatformImage`/`PlatformFont`/`PlatformColor`; clipboard is `Clipboard.copy`, opening a URL is SwiftUI's `@Environment(\.openURL)`, and the macOS-only modifiers have `platform…` wrappers (`platformTextStyle`). `#if os(macOS)` in a feature view is for genuine layout differences, not API shims (`onDeleteCommand`, the section switcher); reach for a helper in `Platform.swift` first. On iPadOS the menu bar's App menu (`CommandGroup(replacing: .appSettings)`) and the title menu both open the window header's Settings sheet, the menu bar through the `showSettings` focused value; `⌘,` is registered only on that menu bar command. Sandbox/hardened-runtime/entitlements are scoped `[sdk=macosx*]`.
- **One header over the whole window on both platforms**: title (server + menu) leading, the segmented section switcher centre via `.secondaryAction`, the section's actions trailing. A list's filter is a field pinned atop the list (`listFilter`; the system search field on a compact width), never a toolbar search on macOS, where a `.searchable` toolbar search reconfigures the toolbar and reflows the switcher on every section change. macOS gets this from a two-column `NavigationSplitView`. iPad has no toolbar spanning split columns, so `MainSplitView` lays the list and detail out as two panes under one `NavigationStack` bar with `.toolbarRole(.editor)` — the role that keeps the title leading while `.secondaryAction` fills the centre. Never `.principal` on iOS: it replaces the title. That one bar has no per-column region, so a list hands its sort/clear to `listFilter`'s `actions`, never `.sectionListToolbar` directly (Activity, with no filter field, declares its type menu and Clear Events there itself on a compact width, never inside the connection control): they land over the column on macOS, in the tab's bar on a compact width, and beside the filter field on a regular-width iPad.
- **All four sections stay mounted; the switcher only changes which is visible** (`sectionResident(active:)` in `MainSplitView`). Switching a `switch` branch tears a section down and rebuilds it, which lands a heavy section's rebuild inside the switcher's animation. Anything a section needs loads in its own `.task` after it's already on screen. The cost: an inactive section is still in the hierarchy, so anything that publishes to the window — `.sectionListToolbar` items, `.focusedSceneValue` commands — must gate on `@Environment(\.sectionIsActive)`, or Send/Delete would act on a section that isn't showing. `SectionListToolbar` does this already; a new focused value must. A section never declares its own `.inspector`: sibling inspectors in one column compete for the same presentation, so the detail pane hosts one (`SectionInspector`) that shows what the visible section has open, from state in its store.
- **A compact width is tabs, not two panes.** An iPhone, or an iPad in Slide Over or a narrow split (`\.isCompactWidth`), can't hold the list beside its detail or the switcher beside the title, so `MainSplitView` makes each section a `Tab` whose `NavigationStack` roots the section's list and pushes its detail. The sections are still views onto the server: every tab's title is the server with its title menu, and there is never a Servers tab. A list brings its detail on screen through `@Environment(\.showSectionDetail)`, which is nil wherever the detail is already beside it. Activity pushes nothing: its list pane only filters, so its events are the tab's root. Focus Path (⌘L) survives a push (`pathFocusPending`, consumed by the bar when it appears), since a path can't be typed until the request bar is on screen. Sections share one `RequestStore` workspace, so a tab switch parks the outgoing section's request, response, and back/forward and restores the incoming one's (`switchWorkspace`); a server switch discards them all (`resetAllWorkspaces`) and pops the stacks. `TabView` keeps visited tabs mounted, so each tab sets `sectionIsActive` and the per-tab `Header` and `SectionInspector` gate on it. An Activity event opens in a real half-height `.sheet` there, since an adapted inspector opens full height on an iPhone whatever its detents say. On iOS a Media item opens in a real `.sheet` wherever the detail is compact or taller than wide (measured outside the inspector, so opening it can't flip the choice), and in the side inspector otherwise. The sheet zooms out of the tapped poster (`.navigationTransition(.zoom)` against `matchedTransitionSource` on the art, through the `posterZoom` namespace `SectionInspector` hands down); an inspector can't zoom, which is why the phone's Media info is a sheet and not the adapted inspector. The zoom's timing, drag-to-dismiss, and Reduce Motion fallback are the system's — don't restyle them. Any sheet showing Media info carries its own `LightboxOverlay`; the window's is drawn under sheets.
- **A section's list pane only filters or chooses what the detail shows.** On a regular-width iPad, Activity's list pane stays hidden until it has something to list: the panes share one well, so a blank one would be unmarked space pushing the events' zero state off centre. Status and controls for the detail's content live with it: Activity's connection is `ActivityConnectionControl`, the tab bar's accessory on an upright phone (`tabViewBottomAccessory(isEnabled:)`, Activity's tab only — the reason iOS targets 26.1), and elsewhere, where the accessory would span the screen, a glass capsule floating over the bottom of the events (`.safeAreaInset(edge: .bottom)`). Status reads `Connected`, never the server's name — the title already says it. Disconnect-on-server-switch lives in `MainSplitView`, since the list pane isn't mounted on every layout.

## Design: the HIG, as applied here

We follow Apple's Human Interface Guidelines for macOS. Below is how that resolved in this app; when in doubt, read the HIG page, not another app.

**Chrome must earn its place.** Every visible control or label in a header costs attention. Before adding one: is it already shown elsewhere in the window (the title bar names the server — don't repeat it)? Could it be a tooltip, a popover, a menu item, or a Settings default instead? The request bar is `GET [path] [Send]`; keep it that way.

**Layout**
- Two columns at a regular width: the selected section's list, then its detail. Never two segmented controls in the toolbar; SwiftUI has no column-aligned toolbar sections on macOS, so don't try to put items "over" a column. The list is user-resizable (the `NavigationSplitView` column on macOS, `ListDetailPanes` on iPad); the kept width re-clamps to the window on every layout so the detail keeps at least 360 pt, and the drag writes it outside any animation.
- Column layout is narrow: lists use two-line rows, not tables; nothing in the detail may need more than about 360 pt: on macOS an open inspector makes the window hold the list's and inspector's current widths plus the detail's minimum, and when it can't grow, SwiftUI's split view loops until AppKit throws, so a row of fixed-size controls wraps instead (`InfoRowLayout`); response headers are a `Grid` inside the tab's scroll so the request block can scroll with them. Sorting in a narrow list goes in a toolbar menu. A long column (the endpoint catalog, history) is a `SectionColumnList` (`LazyVStack`), never a `List`: on macOS `List` hosts every row in its own `NSHostingView` and measures them all when it appears, so hundreds of rows stall each section switch. Short columns (Activity, Media) keep `List`. A compact width is always iOS, where `List` is lazy, so there `SectionColumnList` is a plain `List`.
- Sheets for short targeted input (save, placeholders); popovers for reference (endpoint docs); never a popover for a warning. No auxiliary windows. A sheet is framed by `SheetScaffold`. Never a fixed width on iOS — an iPhone sheet is the screen's width and clips it; a popover that can adapt to a sheet takes an ideal width, not a fixed one.

**Toolbar placement** — decide this when adding the control, not at review.
- The toolbar is for things that act on *what the column shows*: switching the view, sorting it, clearing it. If a control edits or sends the *object being edited* — the request's path, params, headers, send — it lives beside that object in the request bar. Actions on the request as a whole — documentation, copy, save — are toolbar items over it (`requestScreenActions`): the pushed request screen's bar on a compact width, the trailing end of the bar over the detail elsewhere. If a control acts on a sub-pane (the Response pane's wrap, fold, copy body), it lives in that pane's own header row.
- Values and preferences are never toolbar items: a pop-up in the body, or Settings if app-wide.
- Status and information never go in the toolbar. Title and `navigationSubtitle` are the only text there.
- The trailing slot holds what applies to the section showing. An item two sections share — the server title, the switcher, the section list toggle, the request actions (`RequestToolbarItems`) — is declared once with a stable `ToolbarItem(id:)`. Only what's specific to one section comes and goes with it, and the switch goes through `withoutToolbarFade`: AppKit crossfades the whole toolbar whenever its item set changes, flashing every item that stays. Dim an item that's temporarily unavailable rather than removing it. Aim for at most three trailing items. Declare a detail item at the pane, not from inside a section's content: one declared there fills the toolbar behind it.
- Toolbar items are icon-only `Label`s, no bezels, standard SF Symbols.
- The Refresh Servers class of rare actions belongs in the menu bar only; the toolbar is for what you do repeatedly.

**Menu bar** — Apple's rules, as they land in `AppCommands.swift`.
- The menu bar lists *every* command the app has, because users can hide or customise the toolbar. Toolbar buttons, context-menu items, and keyboard shortcuts are conveniences on top of a menu item, never substitutes for one. The section switcher and the compact tab bar are exempt: they're view navigation, not commands, and stay toolbar-only.
- App-specific commands go in two custom menus between View and Window: **Server** (acts on the selected server) and **Request** (acts on the request in the bar). Don't invent a third menu when one of these fits. No menu item icons.
- Unavailable commands are *dimmed*, never removed — the menu's shape stays stable. Gate on state (`activeServer == nil`, `!requests.isSending`); for commands that act on the visible section, publish a `FocusedValues` action from that view and disable when it's absent.
- Shortcuts: `⌘` primary; `⇧⌘` for the sibling of a `⌘` command; `⌥` rarely; `⌃` never. Only frequent commands get one. Never repurpose a standard shortcut (`⌘Z X C V A F S W N Q ,` and the system's `⌘Space`, `⌘Tab`, `⌘←→`). Taken here: `⌘R` Refresh Servers · `⌘S` Save Request… · `⇧⌘C` Copy as cURL · `⌘↩` Send (runs the built query in Media) · `⌘⌫` Delete History Item · `⌘I` Show/Hide Info (Media poster, Activity event) · `⌘.` Cancel · `⌘L` Focus Path · `⌘[` `⌘]` Back/Forward · `⌘,` Settings · `⌘F` find in body (system). Add new ones to this list.

**Liquid Glass**
- Don't apply `glassEffect` yourself. Glass is the system's controls/navigation layer — toolbar, sidebar, tab bar accessory, `.glassProminent` on Send. The one exception is Activity's connection capsule on iPad and the Mac: a control floating over content, which the HIG allows on a custom control "sparingly". A second one needs the same case: a control, above content, with no system home. Everything in a content pane (status readouts, pagination, badges, cards) uses standard fills: `.fill.tertiary`, `.quaternary`, `.regularMaterial`.
- The detail well (`WellBackground`) is the one sanctioned content-pane translucency: on macOS an `NSVisualEffectView` (`.underWindowBackground`, `.behindWindow`) behind opaque cards and the code document, user-toggleable (`translucentBackground`). Don't extend behind-window vibrancy to other content surfaces. iOS has no desktop behind the window, so its well is the system background under a static accent wash; one well backs every iOS screen and spans both iPad panes, with no pane colour or divider between them. The code surface's background is clear on iOS so the response body draws over the well too; an opaque one turns the pushed body screen into a black slab beside the washed lists. The wash is the only gradient: never animated, never a raw colour.

**Controls**
- Segmented control = switching views. A *value* is a pop-up (`Picker` `.menu`), or a Settings default if it's app-wide.
- One prominent button per view (Send). Destructive actions use `role: .destructive`; only un-undoable ones confirm (Clear History, Sign Out, Delete saved) — Disconnect and Clear Events don't.
- Checkbox for a single minor option in the body (Wrap); switch only for an emphasised or grouped setting. Toggles never in a toolbar.
- Icon-only buttons are `Label("Verb", systemImage:)` + `.labelStyle(.iconOnly)` with a `.help` tooltip, never a bare `Image`, so VoiceOver gets the verb. Decorative symbols get `.accessibilityHidden(true)`. Status colours are always paired with words; the dot is redundant.
- A row in a selectable `List` opens through `.contextMenu(forSelectionType:menu:primaryAction:)` — a tap on iPad, a double-click on the Mac, where a click already selects — never a tap gesture or a row `Button`, which on macOS swallow the table's own click and arrow-key selection. On a compact width a tap neither selects nor runs the primary action, so there the rows are `Button`s that set the selection (Activity's events).
- Spinners are unlabelled; the sentence above them says what's happening. Never "Loading…". Don't block the panel while sending — the spinner replaces Send's icon and the last response stays readable. What needs a server is disabled without one.
- A section's *resting* or *empty-result* state (nothing sent, nothing queried yet, not connected, no events yet, a query or filter that matched nothing) is `ZeroState`, never `ContentUnavailableView`: one muted `subheadline`/`tertiary` sentence, no icon or heading, because the switcher already says where you are. A zero state never carries a button: a section's controls are always on screen. Failures and missing prerequisites stay `ContentUnavailableView` with what to do next (Request Failed, Couldn't Connect, No Libraries, No Servers, a server that isn't reachable).
- A field that takes epoch seconds is never bare: it gets `EpochDateButton` (calendar and Now; the relative ago choices only where the media-query grammar applies — Media filters, operator keys) and an `EpochReadout` under it. Which names are dates is `EpochDate.isEpochName`, shared with the decoded Details, so a field and its read-out never disagree.

**Colour, type, icons**
- System semantic colours only. Anything hashed to a colour maps into the 12-colour system palette, never raw HSL.
- The code surface is coloured by `CodeColors.system`: system hues (`PlatformColor.codeTeal` …) resolved to their Increase Contrast variant in a light appearance and left standard in dark: the code surface is white, where the standard teal, green, and orange fall far under 4.5:1. Add a token colour the same way, never a raw system hue. There are no code themes; don't add a theme setting.
- Text styles for hierarchy; no Light/Thin weights; no hand-set `.tracking`. The code face is Commit Mono, only via `Font.code(_:)` (`Typeface`), never `.monospaced()` or `NSFont.monospacedSystemFont`; rows step it down on iOS through `.codeListRow` (lists) and `.codeDetailRow` (name/value grids), since iOS's text sizes set it far larger than the Mac's. It's for what the machine says: paths, keys, values, types, counts and count badges, timings, status and error readouts. Prose — descriptions, zero states, headings, controls — stays in the system face.
- SF Symbols used for their meaning. There are no OS/brand logos in SF Symbols: host marks come from bundled Simple Icons (`Assets/Hosts`, template vectors) plus `apple.logo`; Windows is hand-drawn.

**Copy**
- Title Case for controls, menu items, headers, empty-state titles; sentence case for descriptions and status lines. Verbs on buttons. Trailing `…` when a control needs more input first (`Save Request…`, `Clear History…`). Errors say what to do, next to the thing that failed.

**Spec**
- The OpenAPI spec is a guide, not truth. `required` is frequently absent, so a documented-but-unsent parameter shows as a hint on a 400, not a block on sending. Documented params feed autocomplete; users can still type anything.

**Animation** — motion is for continuity and feedback, never ambient decoration.
- Animate when something *changes in place* and the user tracks it (a number updating, a disclosure opening, a state flipping), when content *arrives* (a result set, a decoded image, a live event), or to give an action *felt feedback*. Entrances rise-and-fade from near their resting place — never from `scale(0)` or off-screen; stagger a group 30–80ms apart, capped so a long list doesn't cascade, and never let it block interaction. Still banned: anything ambient or looping (breathing controls, shimmer skeletons, animated gradients, parallax) and motion on the code/response body (layout cost). Two loops are allowed, each running only while its state is real and static under Reduce Motion: a loading placeholder's fill breathing in opacity while its content is actually on the way (`PosterSkeleton`, only while `RemoteImage` is still loading; never a shimmer), and Activity's signal rings swelling slowly while the notification stream is connected (`ListeningPulse`). Static layouts stay static.
- SwiftUI idioms: scope every animation to the value that changed with `.animation(_, value:)`, never a bare `withAnimation` around unrelated state. Numbers roll with `.contentTransition(.numericText(value:))`; swapped text crossfades with `.interpolate`, except a status word the user watches change (Activity's Connected ⇄ Disconnected), which rolls letter by letter with `.contentTransition(.numericText())`. Use the system springs rather than hand-tuned curves: `.snappy` for anything that moves, `.smooth` for large layout, `.bouncy` for a landing the user caused (a poster selected, a response arriving) — never for chrome. Leave system components (lists, disclosures, sheets, menus) to their own motion.
- Swaps are asymmetric: what's leaving gets out of the way faster than what's arriving, never a symmetric crossfade. A resting, empty, or error state goes through `restingStateTransition()` (arrives over ~0.3s, leaves in 0.1s; `rising:` only where the state doesn't carry the request bar, which must not move). A section switch cuts the outgoing section and settles the incoming one up 6pt as it fades in — never sideways. A transition's attached animation runs even in an unanimated transaction, so never attach one to rows that a workspace swap (`switchWorkspace`, `reset`) replaces.
- Reduced motion is a first-class variant, not an afterthought: read `@Environment(\.accessibilityReduceMotion)` and collapse movement to a crossfade or an instant change. Colour and opacity may still transition.
- Skills — run the animations.dev skills by phase, not as a sweep:
  - Designing a feature that has any motion in it → `find-animation-opportunities` first (read-only; it also says what should stay still), then `motion-brief` if the motion is more than a value change.
  - Implementing → `animate` for easing, duration, and spring choices; `animation-accessibility` for the reduced-motion variant.
  - Before committing motion code → `review-animations`. If it's a value update behind a `numericText` or a system component's own transition, skip the review; the bar is met.
  - `improve-animations` (whole-codebase audit) only when the user asks for one — the point of this section is to not need it.
  - Naming a motion you can picture but not name → `animation-vocabulary`.

## Working here

- Every change follows the `change-workflow` skill (branch, verify, pre-merge checklist, review, merge on approval); a release follows `release-workflow`. Both are in `.agents/skills/`. A feature is done only when that checklist passes, in the same commit.
- Xcode project uses synchronized groups: add or move files on disk and they're in the target. No `pbxproj` edits.
- `xcodebuild` is the verifier: macOS and the iOS Simulator both build and the tests (Swift Testing, `DevToolsTests/`) pass before a commit; the commands are in `change-workflow`. SourceKit diagnostics in this workspace report the whole module as unresolved ("Cannot find type … in scope"); they are noise.
- NEVER take screenshots (`screencapture`) or script/drive the running app for verification — it grabs the user's whole screen and is disruptive, and multiple app instances clash with their Xcode session. Reason from the code, and leave visual confirmation to the user, telling them precisely what to check.
- Tests are fixture-driven and target contracts (parsers, URL building, spec matching, redaction, cURL). Add one when you add a contract; don't test plumbing.
- Persistence goes through `AppSupportStore`, `Codable`, tolerant of old files (unknown keys ignored, new keys optional).
- A `Local` connection on an iOS device triggers the local-network privacy prompt (`INFOPLIST_KEY_NSLocalNetworkUsageDescription`); the simulator never asks, so networking changes need a device check against a LAN server.
- The Mac app ships as a notarized DMG on the `site/` landing page, deployed to Vercel with the CLI (`release-workflow`), never Git integration: the DMG is gitignored, so a Git deploy ships the page without it. `site/privacy.html` states what the app sends and stores; a change to either (a new host, a new stored file, anything identifying) updates it in the same commit.
- iOS ships through TestFlight (`Tools/upload-ios.sh`). iOS keeps its own version (`MARKETING_VERSION[sdk=iphoneos*]` and `[sdk=iphonesimulator*]`) apart from the Mac's: TestFlight reviews the first build of every version, so iOS stays on its reviewed version between uploads and moves only when it's submitted to the App Store. App Store Connect rejects an iOS icon with an alpha channel, so iOS has its own flattened `icon_ios_1024.png` (`Icon/build-icon.sh` writes it). `PrivacyInfo.xcprivacy` declares the app's required-reason API use (UserDefaults, CA92.1) and no collected data; a new required-reason API (file timestamps, disk space, system uptime, …) needs an entry there or the upload is rejected.
- One commit per coherent change; the message explains why and records the constraint behind any non-obvious choice.
